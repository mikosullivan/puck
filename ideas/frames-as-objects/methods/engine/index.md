The top-level runtime that drives a CVM. One engine per open DB connection: it owns the SQLite handle, tracks the current process, dispatches the frames on that process's stack, and shuts down when nothing is left to run.

Sits above `object` and `frame` — the engine constructs them and calls their methods rather than being one of them.

**Every method on this page must be as efficient as possible.** These are hot paths — most of them run on every statement dispatch — and any cycle saved multiplies out across the whole running program.

## Policy: DB access via cached-statement methods only

**The engine touches the DB only through dedicated per-statement methods.** No ad-hoc `db:exec(...)`, no inline `db:nrows(...)`, no `db:prepare(...)` scattered through engine code. Each SQL the engine needs is its own method on the engine class, and each of those methods lazily caches its prepared statement on the instance.

The rule buys three things:

- **Reuse is guaranteed.** Every SQL string is prepared exactly once per engine instance and reused thereafter.
- **One source of truth per statement.** Each SQL lives in exactly one place — the method that returns its prepared handle. The method IS the definition.
- **Testable in isolation.** Each method can be called on a fresh engine against a test DB — bindings applied, executed, result checked. No cross-statement setup, no engine-state reproduction.

Every cached-statement method follows the same shape: check the cache field on `self`, prepare-and-store if empty, return. The example below (`object_by_pk`) is the pattern; every other one looks the same with different SQL and a different cache-field name.

## Methods

### `object_by_pk`

Takes a primary key and returns the corresponding objects row wrapped as an object. `nil` if no row exists for that pk.

~~~lua
function engine:object_by_pk(pk)
	if not self.stmt_object_by_pk then
		self.stmt_object_by_pk = self.db:prepare(
			"select * from objects where object_pk = ?"
		)
	end

	local stmt = self.stmt_object_by_pk
	stmt:bind_values(pk)
	local row

	for r in stmt:nrows() do
		row = r
	end

	stmt:reset()

	if not row then
		return nil
	end

	return object.new(self, row)
end
~~~

Callers get an object back, not a raw row. From the outside:

~~~lua
local obj = engine:object_by_pk(pk)
~~~

The lazy-prepare + bind + iterate + reset dance stays inside the method. `stmt:reset()` still runs on every call — it's required for reusable prepared statements in lsqlite3, without it the next `bind_values` on the same handle raises.

**Cache field: `self.stmt_object_by_pk`.** First call preps and stores; subsequent calls skip that block and go straight to bind. The `stmt_` prefix keeps the field name from colliding with the method itself (the class table's `object_by_pk` is the method; the instance table's `stmt_object_by_pk` is the cached statement).

`object.new(self, row)` wraps the row as an object instance — dispatch to the right class (HashPrimitive, ArrayPrimitive, scalar) and any per-pk caching live inside `object.new` itself.

### `add_bucket`

INSERTs a HashPrimitive as the bucket for a given owner and returns the new bucket's `object_pk`. Used by [`object:bucket`](https://www.puck.uno/ideas/frames-as-objects/methods/object/#bucket) as the lazy-create branch of the object's `bucket` accessor.

~~~lua
function engine:add_bucket(for_object_pk)
	if not self.stmt_add_bucket then
		self.stmt_add_bucket = self.db:prepare(
			"insert into objects (primitive, bucket_for, owner_role) " ..
			"select 'h', ?1, owner_role from objects where object_pk = ?1 " ..
			"returning object_pk"
		)
	end

	local stmt = self.stmt_add_bucket
	stmt:bind_values(for_object_pk)
	local bucket_pk

	for r in stmt:nrows() do
		bucket_pk = r.object_pk
	end

	stmt:reset()
	return bucket_pk
end
~~~

**Derives `owner_role` from the target.** The `insert … select` reads `owner_role` off the target row and uses it for the new bucket. Callers don't pass owner_role; the bucket naturally inherits the ownership of the object it's a bucket for.

**Uses SQLite `RETURNING`** to hand the new bucket's `object_pk` back in the same round trip. The pk is generated by the default expression on `objects.object_pk` (a UUID via `randomblob`); RETURNING captures it as it lands.

**Also fires the `objects_denormalize_bucket` trigger** inside the same statement. The trigger updates the target row's `bucket_pk` column to the new bucket's `object_pk` — the value RETURNING gives back equals what the target's `bucket_pk` becomes. Callers don't have to re-read the target row to learn its new `bucket_pk`.

**Cache field: `self.stmt_add_bucket`.** Same lazy-prepare pattern as `object_by_pk` — one INSERT with SELECT + RETURNING gets parsed once per engine instance and reused across every bucket creation thereafter.
