# Q0

## Purpose

Q0 is a small JSON query language for working with Mikobase records. The name stands for "query zero": it is Mikobase's built-in first query language, not the only query language the system may support over time.

In the current workspace, Q0 supports:

- `action: "select"`
- SQLite `action: "create"`
- root selection by no qualifier, `class`, or `path`
- narrowing with `then`
- equality filtering with `where`
- path filtering with `path`
- OR branching with `any`

This document describes the Q0 language itself, not any one client library.

Q0 is intended to be the common baseline language that all engines can support. Future engines may also support additional query languages, including languages such as GraphQL.
## Universal Namespace

Mikobase uses Universal Namespace, or UNS, for globally unique object and class names.

A UNS name is a domain name plus a short path. `https://` is implicit and should not appear in the name.

Examples:

- `mikobase.com/record`
- `mikobase.com/class`
- `codex.com/foo`
- `kiera.uno/object`

In the broader object model, `kiera.uno/object` is the root class of all objects. `mikobase.com/record` is the base class for records specifically.

Mikobase uses only minimal implicit class resolution. In a record-class context, a one-segment path is interpreted under `mikobase.com/record`. In a general field or object-class context, a one-segment path is interpreted under `kiera.uno/object`. Beyond that one implicit parent step, full paths are required.


## Narrowing

Q0 is designed around narrowing.

Instead of expressing one large combined AND clause, Q0 applies a sequence of narrowing steps to a current result set.

That means a query is read as:

1. start from some root selector
2. narrow those rows with one condition
3. narrow the surviving rows again
4. continue until the query is finished

## A Q0 Query Is A JSON Object

Every Q0 query is a single JSON object.

Minimal example:

```json
{
	"action": "select",
	"class": ["character"]
}
```

## Current Scope

The current implementation is split by engine:

- PostgreSQL currently supports `select`
- SQLite currently supports `select` and a minimal record `create`

Current SQLite `create` behavior:

- `bucket` is required and must be a JSON object
- `class` is optional and, when present, must be a non-empty string naming an active class id
- successful creates return a hash with `success: true` and the created record `pk`
- the current SQLite `create` path is intentionally narrower than the planned engine-agnostic write API described below

Broader write behavior such as `update`, `delete`, richer class-path handling, and non-SQLite write support is still planned rather than current.

## Planned Write API

The following write design describes the intended public Q0 API after the broader write work is finished. The current SQLite-only `create` implementation is only a partial step toward this shape.

Q0 write requests use plain JSON objects.

Planned top-level request shapes:

```json
{
	"action": "create",
	"class": ["character"],
	"bucket": {
		"name": "Spock"
	}
}
```

```json
{
	"action": "update",
	"pk": "92677339-df86-4f68-9397-999e40cf2c40",
	"bucket": {
		"name": "Spock"
	}
}
```

```json
{
	"action": "delete",
	"pk": "92677339-df86-4f68-9397-999e40cf2c40",
	"if-exists": true
}
```

Planned write rules:

- `create`, `update`, and `delete` are separate actions
- write requests use top-level fields rather than wrapping record data in a nested write object
- `create` requires `bucket`
- `create` may omit `class`; omitted `class` and `class: null` mean use the tenant default record class if present, otherwise the record base class
- `update` requires `pk` and must include at least one of `bucket` or `class`
- `update` treats omitted `class` and `class: null` as no class change
- `update` treats `class: []` as an exact change to the record base class
- `delete` requires `pk`
- `if-exists` is supported only on `delete`
- `if-exists` defaults to `false`
- `class` may be a string, an array of zero or more strings, or `null` where ignoring is allowed
- `class: []` normalizes to `["mikobase.com/record"]` for record-class contexts
- the engine prepends `mikobase.com/record` to a non-null class array when needed
- `pk` must be a string when supplied
- `bucket` must be a JSON object
- `bucket: null` is rejected for `create` and `update`
- `misc` and `enterprise` are allowed only at the top level and are always ignored by core storage engines such as PostgreSQL and SQLite
- `misc` is intended for ad hoc extension metadata
- `enterprise` is intended for stricter organization-level metadata conventions
- custom engines may use `misc` and `enterprise` however they want

## Planned Write Responses

Planned successful `create` and `update` responses remain minimal:

```json
{
	"success": true,
	"results": {
		"pk": "92677339-df86-4f68-9397-999e40cf2c40"
	}
}
```

Planned successful `delete` responses include a `deleted` flag:

```json
{
	"success": true,
	"results": {
		"pk": "92677339-df86-4f68-9397-999e40cf2c40",
		"deleted": true
	}
}
```

If `if-exists: true` is used and no tombstone is written, the planned response is:

```json
{
	"success": true,
	"results": {
		"pk": "92677339-df86-4f68-9397-999e40cf2c40",
		"deleted": false
	}
}
```

## Planned Request Validation

Planned request-shape validation uses `invalid_request` for malformed requests.

Class lookup and lineage resolution failures use distinct error ids.

Shape problems may include:

- missing required fields
- unknown top-level fields
- invalid field types
- invalid `action` values

The planned error shape is:

```json
{
	"success": false,
	"errors": [
		{
			"id": "invalid_request",
			"details": {
				"missing_fields": ["bucket"],
				"unknown_fields": ["foo"],
				"invalid_types": {
					"if-exists": "expected boolean"
				}
			}
		}
	]
}
```

Validation rules:

- use one `invalid_request` error object for request-shape problems
- `details` may include `missing_fields`, `unknown_fields`, and `invalid_types` together
- omit any `details` entry that would otherwise be empty
- use public field names exactly as written in the request
- report all applicable shape problems rather than stopping at the first one
- use a stable sorted order for field names in validation output
- top-level `misc` and `enterprise` are never reported as unknown fields
- for `class`, `invalid_types` should report `expected string, array, or null` when the value is none of those forms
- malformed class-path steps use `invalid_class_path`, not `invalid_request`
- a `class` array may contain only strings
- class ids must be at least one character long
- class ids may contain only letters, numbers, dots, forward slashes, and underscores
- class ids may not contain spaces or any space characters

## Planned Engine Chaining

Q0 is designed to support engine chains.

In an engine chain:

- there may be any number of engines
- an engine may inspect, reject, modify, or forward a request
- an engine may inspect, reject, modify, or forward a response
- core storage engines such as PostgreSQL and SQLite do not need to know about custom policy engines
- custom engines may use top-level `misc` and `enterprise` fields as pass-through extension channels

A firewall or business-rule engine may, for example, allow a query to succeed but redact disallowed `bucket` fields from the response before returning it to the caller.

## Planned Class Errors

Class-related failures should use the most specific error id available.

- malformed class-path steps use `invalid_class_path`
- a syntactically valid class path step that does not resolve under its parent uses `class-not-found`

`invalid_class_path` uses this shape:

```json
{
	"id": "invalid_class_path",
	"details": {
		"requested": ["foo", 123, "Bob & Doug"],
		"errors": [null, "not-string", "invalid-step-name"]
	}
}
```

Rules:

- `requested` and `errors` must have the same length
- each `errors` element is either `null` or a stable per-step reason code
- `invalid_class_path` applies to malformed class arrays such as non-string steps or invalid step names

`class-not-found` uses this shape:

```json
{
	"id": "class-not-found",
	"details": {
		"requested": ["foo", "bar", "gup"],
		"valid": ["foo", "bar"],
		"invalid": ["gup"]
	}
}
```

Rules:

- `requested = valid + invalid`
- `invalid` must be non-empty
- `class-not-found` is used when the exact requested path does not exist, even if some earlier prefix is valid

## Class Contexts

The docs must distinguish record-class paths from field or object-class paths.

Rules:

- in a record-class context, `class: []` means `mikobase.com/record`
- in a field or object-class context, `class: []` means `kiera.uno/object`
- a one-segment class path uses the implicit parent for its context
- a multi-segment class path is taken literally
- `null` means ignore this class field only where ignoring is already valid

A field definition should also distinguish between a field object class and a referenced record class.

For example, a `mikobase.com/reference` field is itself an object-class field type, while its allowed target record class is declared separately.
Class-path input forms:

- a string means a one-element class path
- an array means an explicit class path
- an empty array means the contextual base class
- `null` is allowed only in operational positions that explicitly support ignoring the class field

Declarative schema positions such as field definitions and reference target constraints require a real class path and reject `null`.
For class definitions themselves:

- the top-level `name` may also use string shorthand for a one-element class path
- the class definition should declare whether it is defining a `record-class` or an `object-class`
- in a `record-class` definition, a one-segment `name` is interpreted under `mikobase.com/record`
- in an `object-class` definition, a one-segment `name` is interpreted under `kiera.uno/object`
- this marker belongs on the class definition itself rather than on every ordinary field



## Planned Class Defaults

Tenants may define a default class for new records, but they are not required to do so.

Rules:

- omitted `class` and `class: null` in `create` mean use the tenant default class if present, otherwise the base class
- `class: []` and `class: ["mikobase.com/record"]` mean the record base class explicitly, even when a tenant default exists
- the tenant default affects only `create`
- the tenant default is represented by a simple boolean marker in class history
- at most one active class per tenant may be marked default
- if no tenant default exists, `create` falls back to the record base class

## Planned Class Actions

Q0 is expected to grow class-focused actions because classes are first-class objects in Mikobase.

Planned class actions include:

- changing the tenant default class as a versioned class change
- renaming a class
- deleting a class

Classes are intended to become true first-class objects in Mikobase. The class object class id is `mikobase.com/class`, and this will require significant refactoring in the current SQLite and PostgreSQL engines.

Class rename rules:

- renaming a class preserves the underlying class identity and structure
- descendant visible class paths update after a rename
- records in renamed classes present the new class paths after the rename
- historical reads before the rename continue to show the old names and old paths
- sibling-name collisions use `class-name-conflict`
- rename validation uses normal class-id naming rules before collision checks

Class delete rules:

- classes may be marked deleted
- a class delete fails while any records still belong to that class or to any descendant class
- class deletion is cascade-fail rather than cascade-delete
- class tombstones clear class business fields and keep only identity, tenant identity, `active = false`, and engine-managed metadata
- present-time class reads hide deleted classes
- historical reads may still show classes that were active at the cutoff timestamp
- targeting a deleted class for record assignment or rename uses `class-deleted`
- class delete may use `if-exists`
- with `if-exists: true`, deleting an already deleted class or a class path that never existed returns success with `deleted: false`

## Planned Connection Modes


Every Mikobase connection must be opened with an explicit mode. There is no default mode.

Valid public mode strings:

- `rw`
- `wr`
- `r`
- `w`

Rules:

- mode parsing is case-insensitive
- surrounding whitespace is rejected rather than trimmed
- `rw` and `wr` are exactly equivalent and normalize to `rw`
- `r` means read-only
- `w` is reserved for future write-only support
- syntactically invalid mode strings use `invalid-mode`
- syntactically valid but unsupported modes use `mode-not-supported`
- if an engine accepts a mode, it must enforce it faithfully or fail to open

A read-only connection rejects state-changing Q0 actions with `read-only-connection`.

`action-not-supported` is reserved for actions the engine or mounted context does not implement at all.

Connection mode is part of the public Mikobase model, but backend-specific enforcement remains engine-specific.

## Planned Request Limits


Q0 currently defines no public limit on class-path length or total request size.

A future engine may enforce a request-size limit as an engine-configurable operational rule.

When that happens, the recognized Q0 error id is `request-too-large`.

## Planned Aggregation

An engine may aggregate or bolt on multiple backends and present them as one logical Mikobase.

Aggregator rules:

- the engine presents a consistent set of classes and records to the client
- namespace collisions are handled by the engine before anything is exposed
- the engine may rewrite identifiers internally as long as the public view is stable
- the engine may synthesize stable derived classes or records
- writes are allowed only when the engine knows how to map them cleanly to underlying backends
- some mounted sources may be read-only while others are writable
- responses may include a top-level `provenance` field when an engine chooses to expose source information

An engine may also adapt an external API or other non-database system as a virtual Mikobase database.

Such an adapter engine may support only part of the Mikobase model, such as read-only classes and records.

## Planned Transactions


Q0 reserves the public action names `transaction`, `commit`, and `rollback`.

This transaction model is intentionally a Q0 conversation model, not a plain SQL-style transaction model.

In Q0, a transaction may commit and remain alive, and it may roll back and remain alive. Commit advances the transaction's checkpoint. Rollback returns the transaction to its most recent checkpoint.

Transaction ids are storage-engine identifiers. Q0 requires only that they be strings.

The connection always has exactly one current transaction at a time.

Starting a nested transaction makes that new transaction the current transaction.

`transaction` starts a new transaction:

```json
{
	"action": "transaction"
}
```

Successful transaction-control responses use a common shape:

```json
{
	"success": true,
	"details": {
		"id": "some-string-id",
		"current": "some-string-id",
		"invalidated": []
	}
}
```

Request rules:

- `transaction` does not require `details.id` in the request
- `commit` and `rollback` must supply `details.id`
- missing or non-string `details.id` values on `commit` and `rollback` are `invalid_request`
- unknown transaction ids use `transaction-not-found`
- transaction ids invalidated by an ancestor rollback use `transaction-invalidated`

Checkpoint rules:

- a self-commit keeps the current transaction alive and establishes a new checkpoint
- a self-rollback keeps the current transaction alive and returns it to its start state or most recent commit checkpoint
- a self-commit or self-rollback returns an empty `invalidated` array

Nested transaction rules:

- if `tr3` is current and the client commits ancestor `tr1`, the engine commits in descendant-first order: `tr3`, then `tr2`, then `tr1`
- after that commit cascade, `tr3` remains the current transaction
- if `tr3` is current and the client rolls back ancestor `tr1`, the engine rolls back `tr1` and invalidates descendant transactions such as `tr2` and `tr3`
- an ancestor rollback invalidates every descendant transaction beneath the target transaction
- invalidated descendant transaction ids remain known to the engine so later uses can return `transaction-invalidated`

Example mental model:

```text
tr1
  tr2
    tr3
```

In that stack:

- commit `tr3`: commit `tr3`, keep working in `tr3`
- rollback `tr3`: restore `tr3` to its checkpoint, keep working in `tr3`
- commit `tr1`: commit `tr3`, then `tr2`, then `tr1`, and keep working in `tr3`
- rollback `tr1`: roll back `tr1`, invalidate `tr2` and `tr3`, and stop using those descendants

## Planned Delete Semantics


The planned delete model is append-only.

A `delete` writes a tombstone version with `active = false`.

That tombstone clears all business fields from the deleted version:

- no `bucket`
- no `custom_classes`
- no class information

Present-time reads should not return records whose latest visible version is a tombstone.

Temporal reads using a cutoff timestamp may still return a record if it was active at that cutoff.

## `select`

A `select` query reads current visible records in the current tenant.

The root `select` may start from:

- no qualifier, which means all visible current records
- `class`
- `path`

For `select`, `class` is a prefix path filter over normalized class paths.

The built-in record base class is `mikobase.com/record`. It is the base class for records, not the root of every object class path.

These queries are equivalent:

```json
{"action":"select"}
```

```json
{"action":"select","class":null}
```

```json
{"action":"select","class":[]}
```

```json
{"action":"select","class":["mikobase.com/record"]}
```

### Root By No Qualifier

Use a bare `select` to begin from all visible current records.

```json
{
	"action": "select"
}
```

Design note:

- a bare root `select` is best reserved for queries whose main point is to return all records
- using a bare root `select` together with further narrowing is usually poor Q0 style
- conceptually, every narrowing sequence already starts from the current full row set before it is narrowed

In most cases, a more specific root such as `class` or `path` communicates intent better.

### Root By `class`

Use `class` to begin from records whose normalized class path begins with the supplied class path.

Class paths are path-like traversal through the inheritance tree. Each segment is interpreted relative to its parent, and a class id only needs to be unique within its parent class.

```json
{
	"action": "select",
	"class": ["character"]
}
```

This prefix matching is inheritance-aware. For example, `{"action":"select","class":["foo"]}` matches both `["mikobase.com/record","foo"]` and `["mikobase.com/record","foo","bar"]`.

### Root By `path`

Use `path` to begin from records whose `bucket` matches a path expression.

```json
{
	"action": "select",
	"path": ["title", "Threshold"]
}
```

## `then`

Use `then` to narrow the rows produced by the previous step.

```json
{
	"action": "select",
	"class": "character",
	"then": {
		"where": {
			"name": "Spock"
		}
	}
}
```

Each `then` step narrows the current result set. It does not start over from all records.

## `where`

`where` is a simple equality filter.
